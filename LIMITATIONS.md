# Limitations

Written from direct experience building this repo, not a checklist filled in
after the fact. If something here contradicts a claim elsewhere in the repo,
this file is the one to trust.

## Circuit construction

- **The hand-rolled Stim circuit (`circuits/lattice_surgery.py`) does not work
  and is not used for any reported result.** Its layout and CNOT schedule are
  verified to exactly reproduce Stim's own rotated-memory reference (a real
  passing test), and its spacelike observable's *value bounds* are sane, but
  `circuit.detector_error_model()` still reports a detector-level
  inconsistency near the merge seam that was never fully closed. Three tests
  documenting this are marked `xfail(strict=True)` in
  `tests/test_lattice_surgery.py` rather than deleted, specifically so this
  doesn't quietly get "fixed" by loosening an assertion. Everything reported
  in this repo comes from the TQEC backend (`circuits/tqec_backend.py`)
  instead.
- **TQEC's `k` scales patch distance and merge/round duration together, and
  this was checked at the API level, not just observed empirically.**
  `tqec.compile.graph.TopologicalComputationGraph.generate_stim_circuit`
  takes exactly one `k: int` for the *entire* compiled block graph
  (`.venv-tqec/lib/python3.12/site-packages/tqec/compile/graph.py`,
  `generate_stim_circuit`/`to_layer_tree`), and `compile_block_graph`'s
  `block_temporal_height` (merge/round duration) is a `LinearFunction` of
  that same single `k` (`.venv-tqec/.../tqec/compile/compile.py`,
  `compile_block_graph`). There is no per-cube or per-pipe override —
  two cubes in one block graph cannot be given different distances, and
  the routing pipe cannot be given an independent width, without patching
  TQEC's own `Template`/layer-generation internals (the objects that turn
  a `k` into a concrete plaquette layout). That is a project-sized
  undertaking in its own right — exactly the "circuit construction eats
  the semester" trap design §11 warns about — so it was not attempted here.
  `circuits/configurations.py`'s `routing_widths` sweep parameter exists
  but is only exercised by the (non-working) hand-rolled builder. Any claim
  about routing-geometry effects, or unequal-distance patches (part of H3),
  remains untested and is a real gap in H3's evidence, not an oversight.
- **Spacelike and timelike observables come from *separate* circuits**, not
  one circuit with two labels per shot. TQEC's block-graph ports can only be
  filled with one logical basis at a time, so a given generated circuit
  carries exactly one observable. This is why every graph carries a
  `head_id` rather than a two-column label, and why E7's spacelike/timelike
  comparison trains and evaluates two separate models rather than one model
  on mixed data with both labels available.
- **Only equal-distance patches are supported.** `build_lattice_surgery_circuit`
  and `tqec_backend.build_block_graph` both raise `NotImplementedError` for
  `patch_a.distance != patch_b.distance`. Unequal-distance merges (relevant
  to some real lattice-surgery use cases) are unimplemented, not just
  untested.
- **Region/phase labels are inferred, not annotated.** TQEC's compiled
  circuit carries no explicit "this ancilla is patch A vs routing" metadata.
  `data/spacetime_labels.py` recovers it by finding ancillas that are active
  only during a short, interior span of rounds — verified to work at two
  code distances (k=1, k=2), not proven in general. A sufficiently unusual
  block-graph shape could break this heuristic silently (it would produce
  *some* label, not an error).

## Scale of everything reported, and what the real run actually showed

`results/main_table.md` and `results/ABLATIONS.md` are real: 8 seeds each,
30000 shots, 20 epochs, generated by `scripts/reproduce.sh`
(`experiments/run_all.py` + `experiments/run_ablations.py`) at the tuned
hyperparameters from `results/HPARAM_SEARCH.md`, not smoke-test placeholders.
The 3-seed/p=0.002/3000-shot numbers from an earlier pass (still described
below for the record) are archived in `results/archive_pre_tuning/`.

### A first version of this section was wrong, and here is the corrected story

The first "credibility" run used p=0.008 and reported that every
lattice-surgery experiment (E3, E5, E6, E7, E9) sat within noise of 0.50
(chance), diagnosed here as "undertraining — scale up shots/epochs." **That
diagnosis was wrong**, caught by a reviewer's four-step diagnostic protocol
before any time was wasted chasing it with more compute:

1. **Label balance on surgery shots at p=0.008**: raw observable flip rate
   0.486 — indistinguishable from a coin flip.
2. **MWPM on the surgery DEM at the same p**: 0.360 decoded error rate.
   Since MWPM is independently validated (`circuits/validate.py`'s week-5
   gate) and still failed to do much better than the raw rate, the problem
   was the circuit/parameter choice, not the GNN.
3. **Graph sanity**: the surgery circuit runs ~15 total rounds (TQEC's
   merge/pre/post pipeline) versus the plain memory circuit's 3, with 10x
   more detectors and ~30x higher mean fired-detector count at the same p.
   A sweep (p=0.001 to 0.008) showed MWPM's decoded rate degrading
   *smoothly and monotonically* from 1.3% to 36% — the signature of running
   well above threshold for a small, many-round code, not a broken or
   randomly-labeled observable.
4. **Overfit test**: at a genuinely decodable p (0.002), the GNN drove
   training loss to ~0 and 100% accuracy on a fixed 100-shot batch within
   ~60 steps. The model/loss/optimizer plumbing was never the problem.

Root cause: **p=0.008 was chosen for the "credibility" runs without
cross-checking it against this circuit family's actual threshold**
(~0.0035, already measured earlier in the same session via
`binary_search_threshold`, and simply never consulted again when picking a
`p` for the later multi-seed runs). E2's own GNN-vs-MWPM gap at p=0.008
(0.047 vs 0.013, 3.6x) was a *separate*, genuine training-budget issue —
confirmed by rerunning it at more epochs and watching the gap narrow
(0.048 → 0.036 from 3 to 15 epochs) — but it does not explain E3/E5's near
identical, flat 0.485/0.487, since real undertraining lands somewhere
between chance and good, not pinned exactly at chance regardless of
training. A guardrail (`data/generate.py`'s `sample_shots(...,
warn_near_chance=True)`, on by default) now warns loudly whenever a
sampled observable's flip rate is within 0.4 of chance, specifically so
this class of error surfaces before a multi-seed run, not after one.

**Corrected results, p=0.002 (a validated sub-threshold rate for this
circuit), 3000 shots, 8 epochs, 3 seeds:**

| experiment | decoder | logical error rate |
|---|---|---|
| E2 (memory) | gnn | 0.0091 ± 0.0042 |
| E2 (memory) | mwpm | 0.0006 ± 0.0004 |
| E3 (zero-shot to surgery) | gnn | 0.3206 ± 0.0356 |
| E5 (surgery-trained) | gnn | 0.1156 ± 0.0038 |
| E7 (surgery, spacelike) | gnn | 0.1124 ± 0.0024 |
| E7 (surgery, spacelike) | mwpm | 0.0484 ± 0.0015 |
| E7 (surgery, timelike) | gnn | 0.2794 ± 0.0664 |
| E7 (surgery, timelike) | mwpm | 0.0982 ± 0.0112 |

This is a coherent, interpretable picture for the first time: the GNN
clearly learns on both memory and surgery data; zero-shot transfer (32%)
is much worse than surgery-specific training (11.6%), a real H1/H3-shaped
finding rather than a chance artifact; and the GNN still trails MWPM by a
real margin everywhere (memory: 15x; surgery spacelike: ~2.3x; surgery
timelike: ~2.8x) that further training/tuning would need to close before
any "GNN matches or beats MWPM" claim could be made.

### A third pass: real hyperparameter tuning, then a much larger run (this is current)

The 15x memory gap above was never tuned against — every number so far used
the design doc's own default hyperparameters (`hidden_dim=64, num_layers=4,
conv_type="gat", heads=4, lr=1e-3`), because a real search wasn't practical
on CPU. Adding GPU support (`experiments/common.py::train_gnn`/
`default_device`, an RTX 4060 that had been sitting idle) changed that:
`experiments/hparam_search.py` ran 58 trials (a cheap 1-seed ranking pass
over 40 sampled configs, then a 3-seed confirmation pass over the top 6) and
found `hidden_dim=64, num_layers=6, conv_type="transformer", heads=2,
lr=3e-4, weight_decay=1e-4` — full results in `results/HPARAM_SEARCH.md`,
including a follow-up check (3x the epochs, 2x the test shots) confirming
the winner was converged, not undertrained.

**This did not fully close the E2 gate.** The GNN still does not beat MWPM
on memory — the gap narrowed from ~15x to a stable ~1.8x-1.9x and stopped
improving with more training. That is reported as the honest outcome of the
search, not softened.

Two real, GPU-specific bugs were found and fixed while running this search
and the sweeps below — worth knowing about if you rerun any of this:
1. `experiments/common.py::evaluate_gnn` (and `e4_localization.py`'s
   heatmap) used to collate *every* graph being evaluated into one single
   `Batch` and forward it in one shot. Fine for small memory-circuit test
   sets; it CUDA-OOM'd an 8GB card on large k=2 surgery-circuit test sets
   (thousands of graphs, each far larger than a memory graph, through a
   6-layer TransformerConv at once). Fixed by chunking evaluation into
   256-graph batches — `evaluate_gnn` now takes an `eval_batch_size` and
   accumulates a running wrong/total count instead of materializing one
   giant batch.
2. `train_gnn` builds a fresh model on every call, and PyTorch's CUDA
   caching allocator doesn't release memory reserved for a since-discarded
   model when graph sizes change between calls (e.g. `experiments/
   e7_threshold_sweep.py` sweeping k=1 then k=2 surgery circuits
   repeatedly) — enough repeated size changes fragmented the allocator
   into another OOM even after fix #1. Fixed with `torch.cuda.empty_cache()`
   at the start of every `train_gnn` call.

With the tuned hyperparameters and, once these two fixes landed, a real
scaled-up run (30000 shots, 20 epochs, 8 seeds — up from 3000/8/3 — at the
same validated p=0.002), the picture changed substantially and not
uniformly in the "better" direction:

| experiment | decoder | logical error rate (old, 3 seeds) | logical error rate (new, 8 seeds) |
|---|---|---|---|
| E2 (memory) | gnn | 0.0091 ± 0.0042 | 0.0013 ± 0.0002 |
| E2 (memory) | mwpm | 0.0006 ± 0.0004 | 0.0007 ± 0.0002 |
| E3 (zero-shot to surgery) | gnn | 0.3206 ± 0.0356 | **0.4207 ± 0.0305** |
| E5 (surgery-trained) | gnn | 0.1156 ± 0.0038 | 0.0622 ± 0.0013 |
| E7 (surgery, spacelike) | gnn | 0.1124 ± 0.0024 | 0.0621 ± 0.0015 |
| E7 (surgery, spacelike) | mwpm | 0.0484 ± 0.0015 | 0.0491 ± 0.0012 |
| E7 (surgery, timelike) | gnn | 0.2794 ± 0.0664 | 0.1239 ± 0.0027 |
| E7 (surgery, timelike) | mwpm | 0.0982 ± 0.0112 | 0.0990 ± 0.0014 |

Surgery-*trained* performance (E5, E7, E9) improved dramatically — spacelike
now trails MWPM by only ~1.26x (was ~2.3x) and timelike by ~1.25x (was
~2.8x), both a real result given MWPM's own numbers barely moved (as
expected — MWPM doesn't use the GNN's hyperparameters at all; this is the
tuning actually helping the model, not measurement noise). **Zero-shot
transfer (E3) got measurably *worse*** (32% -> 42% error), not better, going
the opposite direction from every surgery-trained metric.

**This section originally offered a guess here (a deeper/tuned architecture
"specializing harder" to memory statistics) and explicitly flagged it as
untested. It was tested — with `experiments/e3_isolation_check.py` — and
the guess was wrong; here is the corrected story, in the same spirit as
the p=0.008 correction above.** The isolation check trains the *old*,
untuned hyperparameters (`hidden_dim=64, num_layers=4, conv_type=gat`) at
the *new*, larger scale (30000 shots, 20 epochs, 8 seeds) — same
architecture as the original 32% result, same scale as the 42% result —
to separate which factor actually drives the regression:

| condition | E2 (memory) rate | E3 (zero-shot) rate |
|---|---|---|
| old hyperparams, old scale (3000/8/3 seeds) | 0.0091 ± 0.0042 | 0.3206 ± 0.0356 |
| old hyperparams, **new scale** (30000/20/8 seeds) | 0.0017 ± 0.0002 | **0.5171 ± 0.1532** |
| new (tuned) hyperparams, new scale (30000/20/8 seeds) | 0.0013 ± 0.0002 | 0.4207 ± 0.0305 |

Old hyperparameters at the new scale land at 51.7% zero-shot error —
*worse* than the tuned-architecture result, not closer to the old 32%.
**The regression is driven by training scale (more shots/epochs of
memory-only training), not by the tuned architecture** — the opposite of
what the untested guess said. The std at old-hp/new-scale is also
enormous (±0.1532, individual seeds ranging 0.29 to 0.67), meaning zero-shot
transfer under more memory training is not just worse on average but
substantially less stable across seeds than either other condition. The
most defensible reading now: training a memory-only decoder for longer, on
more data, makes it fit the memory distribution more precisely, which a
memory-only metric (E2) rewards unconditionally but which pulls the
decoder's decision boundary further from whatever generalizes to surgery
data — independent of model capacity/architecture, since the untuned
4-layer GAT model shows the same effect, if anything more severely. This
is now a genuine, *tested* H1 finding rather than a plausible-sounding
guess: **more memory-training budget is not a free lunch for a decoder
meant to eventually transfer to lattice surgery, regardless of
architecture** — and it is a caution against assuming "better at E2" means
"better positioned for H1," which the original E2-gap-closing motivation
for this whole search implicitly assumed. See `results/E3_ISOLATION_CHECK.md`
for the raw per-seed numbers.

H4's threshold curves (`experiments/e7_threshold_sweep.py`,
`results/THRESHOLD_SWEEP.md`, `results/timelike_threshold.png`) are new
in this pass too — MWPM's pseudo-threshold (k=1 vs k=2 crossing, dense
p-sweep, 20000 shots/point) came out at p≈0.0033 (spacelike) and p≈0.0030
(timelike), consistent with the ~0.0035 figure measured earlier in this
project by a different method (`binary_search_threshold`) — a real
cross-check, not just a repeated number. The GNN's own curves do **not**
show a crossing in the swept range (0.0008-0.02): at every swept `p`, its
k=2 (d=5) error rate was at or above its k=1 (d=3) rate, i.e. more code
distance did not help the GNN the way it helps MWPM, at least not within
this p range and training budget. That is itself a real, if negative, H4
finding — a decoder can be evaluable on lattice surgery (H1) and still not
show the *distance-scaling* behavior a decoder needs to be useful as `d`
grows.
- **The union-find baseline (`baselines/union_find.py`) uses two
  documented simplifications**: whole-edge growth per round instead of
  scheduled half-edges (slightly suboptimal but still a valid decoder —
  verified on hand-checkable tiny cases), and it silently drops DEM error
  mechanisms of weight ≥3 that `decompose_errors=True` couldn't fully
  reduce (a real, non-trivial fraction of mechanisms — see the module's
  own docstring for the measured proportion). Its reported accuracy is a
  lower bound on what a full peeling-decoder implementation would achieve.
- **E4's localization heatmap is a proxy, not a direct measurement.** There
  is no ground-truth record of *which* physical error caused a given wrong
  prediction. The heatmap reports P(decoder wrong | shot has ≥1 fired
  detector in this round/region), which correlates with but is not
  identical to "the error was located here." `results/spacetime_heatmap.png`
  is current — regenerated in the same tuned-hyperparameter, 8-seed run as
  `main_table.md` above (matching file timestamps) — but it uses
  `first_memory_model` (the seed=0 memory-trained model, per
  `experiments/run_all.py`), not the surgery-trained model from E5, so it
  illustrates zero-shot-style behavior specifically — the mode that this
  pass's tuning made *worse* (see above), not the better-performing
  surgery-trained one.
- **`results/ABLATIONS.md` is now at the tuned hyperparameters and the
  8-seed/30000-shot/20-epoch scale** (leave-one-out variants: region/phase
  features removed, DEM edges removed, radius edges removed, shallower
  (4 vs the tuned 6 layers — the ablation baseline was updated to 6 layers
  to match the search winner, so this variant is a genuine "remove depth"
  comparison rather than the old baseline=4 version's "closest available
  direction is deeper, not shallower"), and normalization removed):

  | variant | mean rate | std | delta vs baseline |
  |---|---|---|---|
  | baseline (all components on) | 0.0622 | 0.0021 | — |
  | region/phase features removed | 0.0620 | 0.0035 | -0.0002 |
  | DEM edges removed (radius-only) | 0.0640 | 0.0021 | +0.0019 |
  | radius edges removed (DEM-only) | 0.0563 | 0.0016 | **-0.0059** |
  | shallower (4 layers vs 6) | 0.0633 | 0.0021 | +0.0012 |
  | normalization removed | 0.0645 | 0.0042 | +0.0024 |

  Baseline (0.0622 ± 0.0021) matches E5's 0.0622 exactly — a real
  cross-check, both numbers coming from the same config through two
  different code paths. Two findings stand out from noise here at n=8
  (previous n=3 pass could not resolve this): removing radius edges and
  keeping only DEM-derived edges is *better* than the combination
  (-0.0059, roughly 3x its own std) — radius edges may be adding noisy
  connections DEM edges don't need — and region/phase features removed is
  essentially a no-op (-0.0002) even though those are the features that
  carry lattice-surgery structure in principle, suggesting the model
  leans on DEM/geometric edge structure more than on the explicit
  region/phase one-hots at this scale. Normalization removed (+0.0024) and
  shallower (+0.0012) are smaller, same-order-as-std effects, consistent
  with (but not strong independent confirmation of) the hyperparameter
  search's own preference for `use_norm=True` and deeper (6-layer) models.
  None of this is run through a significance test (see "Statistical
  rigor" below) — "roughly 3x std" is a heuristic read, not a p-value.
- **E6's high variance is not just a "too few configs" artifact — tested,
  and it persists.** `main_table.md`'s E6 row uses `distances=(3,5)`, which
  gives `held_out_split` exactly 2 configurations (1 train, 1 held-out) —
  about as thin as this metric can be. `experiments/e6_extended.py`
  (`results/e6_extended.jsonl`, `results/E6_EXTENDED.md`) reruns it with
  `distances=(3,5,7)` (2 train configs, 1 held-out) at the same 8 seeds,
  30000-shot scale. The result barely changed: held-out rate
  0.2210 ± 0.0933 (extended) vs. 0.2224 ± 0.1014 (original) — adding a
  third configuration did not meaningfully reduce the variance. Looking at
  the per-seed breakdown explains why: which specific distance ends up
  held out (a random draw per seed) dominates the result far more than the
  number of configs does — when `k=3` (`d=7`, the hardest/largest
  configuration in the sweep) is the one held out (2 of 8 seeds here), the
  generalization gap is large and positive (+0.25, +0.27 — genuinely
  worse on the held-out config); when `d=3` or `d=5` is held out instead,
  the gap is small or even *negative* (held-out performs as well as or
  better than train, in 5 of the other 6 seeds). **This "configuration
  generalization gap" metric, as currently defined, is confounded with
  which difficulty level happens to be held out** — it is not a clean,
  single-number measure of how well a model extrapolates to unseen
  configurations in general. A more informative version of E6 would
  report held-out results *per excluded configuration* rather than pooling
  across whichever configuration a given seed's random split happened to
  exclude; that redesign wasn't attempted here.

## Statistical rigor

- `experiments/report.py` aggregates mean ± std across seeds and flags
  `(n=k, INSUFFICIENT SEEDS)` for any group with fewer than 3 — the
  current `results/main_table.md` and `results/ABLATIONS.md` both use
  n=8. n=8 is a real improvement over the earlier n=3 pass (visible in
  most stds shrinking considerably in the table above), but still small by
  the standards of a rigorous confidence interval — treat std as a rough
  noise estimate, not a formal CI, especially for E6 (config
  randomization), whose std stayed large (±0.10) even at n=8, i.e. this
  metric is genuinely high-variance across seeds, not just under-sampled.
- No confidence intervals, significance tests, or corrections for multiple
  comparisons are computed anywhere in the ablation or comparison tables.
  At n=8 several E7/E9 deltas now look large relative to std where they
  didn't at n=3 (e.g. the spacelike/timelike gap-narrowing in the table
  above), but nothing here has been run through an actual hypothesis test
  — "looks large relative to std" is suggestive, not a rejected null.
- **Four real bugs were found and fixed while actually producing the
  results/ files** (not while writing code against synthetic test data),
  which is exactly the kind of thing this section exists to surface rather
  than bury:
  1. `experiments/e3_zeroshot.py`, `e5_surgery_trained.py`, and
     `e6_config_randomization.py` didn't record which physical error rate
     `p` a result came from, so rerunning `scripts/reproduce.sh` at a
     different `--p` silently merged incompatible rows into one aggregate
     — caught by actually rerunning it at a different `p` and noticing the
     mixed group.
  2. `experiments/run_ablations.py` defaulted to the same output file as
     `run_all.py`'s own single-config E9 stage, so the 5 "component
     removed" ablation variants would silently mix into `main_table.md`'s
     one E9 summary row — caught by inspecting the raw
     `results/e9_ablations.jsonl` after a full run and finding 6 different
     configs where there should have been 1.
  3. `p=0.008` was picked for an early multi-seed "credibility" run
     without cross-checking it against this circuit's actual measured
     threshold (~0.0035), driving every lattice-surgery experiment to a
     raw observable flip rate of ~0.49 (indistinguishable from chance) —
     first misdiagnosed here as "undertraining." Caught by a reviewer's
     four-step diagnostic (label balance → MWPM on the surgery DEM →
     graph sanity → overfit test), not by this repo's own process, which
     is precisely why `data/generate.py` now has a `warn_near_chance`
     guardrail on by default.
  4. **The GPU-era one**: `evaluate_gnn` and `e4_localization.py`'s
     heatmap computation collated an entire test set into one `Batch` and
     forwarded it in a single call — silently fine at small scale, and it
     CUDA-OOM'd partway through the first real `experiments/
     e7_threshold_sweep.py` run at k=2 (large surgery graphs, thousands of
     them, through a 6-layer TransformerConv, all at once). Caught by
     actually hitting the crash mid-sweep, not by review. Fixed by
     chunking evaluation into 256-graph batches (see the "third pass"
     section above for the second, related fragmentation bug this
     surfaced and its fix).
  5. **`train_gnn`'s `seed` never actually made model initialization
     reproducible.** It seeded the numpy RNG used for minibatch shuffling,
     but `GNNDecoder`'s weight initialization draws from PyTorch's global,
     un-seeded RNG — so "seed=3" on two different runs (or even two calls
     within the same long-running driver, since global RNG state carries
     over between calls) did not produce the same initial weights. Every
     multi-seed result in this repo is still statistically valid (each
     "seed" was a genuinely independent random trial regardless), but the
     specific claim "pass --seed N to reproduce this exact number" was
     false until `train_gnn` started calling `torch.manual_seed(seed)`
     before constructing the model. Caught by code inspection while
     writing this section, not by a failing test — there wasn't one, since
     nothing checked bit-exact reproducibility across processes.
  All five are fixed (separate result files; `p`/`k` are now recorded
  fields; the near-chance guardrail; corrected `p` and training budget in
  `scripts/reproduce.sh`; chunked evaluation + CUDA cache clearing;
  `torch.manual_seed`), but their having existed at all — especially #3,
  which invalidated an entire round of "real" multi-seed evidence, #4,
  which would have silently capped how large a test set any future
  experiment on this repo could safely use, and #5, which was never
  caught by any test — is worth knowing if you're deciding how much to
  trust the numbers in this repo versus rerunning them yourself. **Because
  of #5, none of the `results/` files checked into this repo (all
  produced before the fix) are bit-reproducible from their `--seed`
  alone** — rerunning will give a different-but-statistically-comparable
  set of independent trials, not the identical numbers.

## Experiment tracking

- **No public W&B dashboard.** `wandb` logging is integrated
  (`models/train.py`'s `wandb_run` hooks in `train_step`/`train_epoch`,
  and `experiments/wandb_demo_run.py` as a runnable example) but has never
  been run against a live account. The original plan was wandb's
  anonymous mode (no account needed on either end), but that turned out
  not to work: confirmed empirically, `wandb.init(anonymous="allow")` on
  the installed SDK (0.29.0) prints "The anonymous setting has no effect
  and will be removed in a future version" and then hard-requires a real
  API key via `wandb login` regardless of the anonymous flag. Running
  `experiments/wandb_demo_run.py` for real just needs `wandb login` first.

## What was not attempted

- No comparison against AlphaQubit, other published GNN decoders, or any
  external baseline beyond MWPM and the in-repo union-find implementation.
- No real hardware noise model (e.g. from a specific device's calibration
  data) — only Stim's/TQEC's uniform depolarizing model.
- **Done in this pass, previously listed here as not attempted**: a real
  spacelike/timelike threshold curve (`experiments/e7_threshold_sweep.py`,
  `results/THRESHOLD_SWEEP.md`, `results/timelike_threshold.png`) — see
  the "third pass" section above for what it found (MWPM thresholds
  cross-checked against an independent earlier measurement; the GNN shows
  no distance-scaling advantage in the swept range). Still not done: a
  *fitted* crossing point with an actual statistical model (logistic fit,
  confidence band on the crossing) — the current pseudo-threshold is a
  linear interpolation between the two bracketing swept `p` values, not a
  fit, and MWPM's `p` grid (10 points) is coarser than a publication-grade
  threshold plot would use.
- Independent routing width / unequal-distance patches (H3) — checked at
  the TQEC API level to be genuinely unsupported without patching TQEC's
  own internals, not just unattempted; see the "Circuit construction"
  section above for the exact citation.
- **Done in this pass, previously listed here as not attempted**: the E3
  zero-shot regression was isolated to training scale rather than the
  tuned architecture (`experiments/e3_isolation_check.py`,
  `results/E3_ISOLATION_CHECK.md`, "third pass" above). Still not done: the

## Environment fragility

- The project depends on two separate Python virtualenvs (`.venv`, Python
  3.14, for stim/pymatching/sinter/torch; `.venv-tqec`, Python 3.12, for
  TQEC) because TQEC does not yet support Python 3.14. If TQEC adds 3.14
  support, that split becomes unnecessary but nothing currently detects or
  simplifies for that case automatically.
